### 1. Context 克隆时的深拷贝不完整 - ✅ 已修复

**文件**: `core/context/context.go`

**问题描述**:
- 克隆的 Context 共享父 Context 的 `context.Context`
- 父 Context 取消时会级联影响克隆的 Context
- 异步操作中可能导致意外的取消

**修复方案**:
```go
// 修复前
newCtx := &Context{
    ctx: ctx.Context(),  // 共享 context
    ...
}

// 修复后
newStdCtx := stdctx.Background()  // 独立的 context

// 复制 trace context（如果存在）
if span := trace.SpanFromContext(ctx.Context()); span.SpanContext().IsValid() {
    newStdCtx = trace.ContextWithSpan(newStdCtx, span)
}

newCtx := &Context{
    ctx: newStdCtx,  // 独立的 context，不受父取消影响
    ...
}
```

**修复效果**:
- ✅ 克隆的 Context 使用独立的 `context.Background()`
- ✅ 自动保留 trace span 信息用于分布式追踪
- ✅ 异步操作不会因父 Context 取消而中断

**测试文件**: `core/context/context_clone_test.go`
- `TestContextClone_IndependentCancellation` - 验证独立取消
- `TestContextClone_TracePreservation` - 验证 trace 保留
- `TestContextClone_EventCopied` - 验证事件克隆

### 3. Lifecycle Manager 的 Stop 超时处理 - ✅ 已修复

**文件**: `lifecycle/lifecycle.go`

**问题描述**:
- 多个组件停止失败时，只返回第一个错误
- 无法知道所有失败的组件
- 调试困难

**修复方案**:
```go
// 修复前
var stopErr error
for i := len(components) - 1; i >= 0; i-- {
    comp := components[i]
    if err := comp.OnStop(ctx); err != nil {
        if stopErr == nil {
            stopErr = &StopError{Err: err}  // 只保存第一个错误
        }
    }
}
return stopErr

// 修复后
var stopErrors []error
for i := len(components) - 1; i >= 0; i-- {
    comp := components[i]
    if err := comp.OnStop(ctx); err != nil {
        stopErrors = append(stopErrors, fmt.Errorf("component %s: %w", comp.Name(), err))
    }
}

// 返回所有错误
if len(stopErrors) > 0 {
    if len(stopErrors) == 1 {
        return &StopError{Err: stopErrors[0]}
    }
    return &StopError{
        Err: fmt.Errorf("multiple components failed to stop: %v", stopErrors),
    }
}
```

**修复效果**:
- ✅ 收集所有组件的停止错误
- ✅ 错误信息包含组件名称
- ✅ 多个错误时返回组合错误
- ✅ 改善了错误追踪和调试能力

**测试文件**: `lifecycle/lifecycle_stop_test.go`
- `TestLifecycleManager_StopMultipleErrors` - 验证多错误收集
- `TestLifecycleManager_StopSingleError` - 验证单错误处理

### 4. AdaptiveRateLimiter CPU 使用率计算不准确 - ✅ 已修复

**文件**: `middleware/adaptive.go`

**问题描述**:
- 使用 goroutine 数量估算 CPU 使用率
- Goroutine 数量与 CPU 使用率无直接关系
- 导致自适应限流策略失效

**修复方案**:
```go
// 修复前
numCPU := runtime.NumCPU()
numGoroutine := runtime.NumGoroutine()
cpuUsage := float64(numGoroutine) / float64(numCPU*100)  // 不准确！

// 修复后
import "github.com/shirou/gopsutil/v3/cpu"

func (arl *AdaptiveRateLimiter) collectMetrics() {
    // 使用真实的 CPU 使用率
    cpuPercent, err := cpu.Percent(time.Second, false)
    if err != nil || len(cpuPercent) == 0 {
        logger.Warn("[AdaptiveRateLimiter] Failed to get CPU usage")
        arl.cpuUsage.Store(-1.0)  // 标记为无效
    } else {
        cpuUsage := cpuPercent[0] / 100.0  // 0.0-1.0
        arl.cpuUsage.Store(cpuUsage)
    }
    
    // 使用 HeapAlloc / HeapSys 更准确的内存指标
    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    memUsage := float64(m.HeapAlloc) / float64(m.HeapSys)
    arl.memoryUsage.Store(memUsage)
}
```

**修复效果**:
- ✅ 使用 gopsutil 获取真实 CPU 使用率
- ✅ CPU 采集失败时使用 -1 标记，调整逻辑会跳过
- ✅ 改进内存使用率计算（HeapAlloc / HeapSys）
- ✅ 自适应限流基于准确的系统指标

**依赖**: `github.com/shirou/gopsutil/v3` (已在 go.mod 中)

**测试文件**: `middleware/adaptive_cpu_test.go`
- `TestAdaptiveRateLimiter_RealCPUMetrics` - 验证真实 CPU 采集
- `TestAdaptiveRateLimiter_CPUFailureFallback` - 验证采集失败处理
- `TestAdaptiveRateLimiter_NoGoroutineBasedCPU` - 验证不使用 goroutine

### 5. HTTPClient Response Body 未关闭 - ✅ 已改进

**文件**: `infra/httpclient/client.go`

**问题描述**:
- `Do()` 方法返回的 Response 需要调用者手动关闭
- 容易遗忘导致连接泄漏

**改进方案**:
```go
// 添加详细文档说明
// Do 执行请求
//
// 重要：调用者必须在使用完 Response 后调用 resp.Close() 关闭响应体，
// 否则会导致 HTTP 连接泄漏。
//
// 示例：
//   resp, err := client.Get(url).Do()
//   if err != nil {
//       return err
//   }
//   defer resp.Close()  // 必须关闭！
//   
//   body, _ := resp.Bytes()
//
// 如果不想手动管理 Response 关闭，可以使用便捷方法：
// - DoJSON()  自动关闭并解析 JSON
// - DoString() 自动关闭并返回字符串
// - DoBytes()  自动关闭并返回字节数组
func (r *Request) Do() (*Response, error) { ... }
```

**现有保护机制**:
- ✅ `DoJSON()` - 已有 `defer resp.Close()`
- ✅ `DoString()` - 已有 `defer resp.Close()`
- ✅ `DoBytes()` - 已有 `defer resp.Close()`
- ✅ `Response.Close()` - 已有关闭方法

**改进效果**:
- ✅ 添加了详细的文档说明
- ✅ 提醒使用者必须关闭 Response
- ✅ 推荐使用自动关闭的便捷方法
- ✅ 减少连接泄漏风险

## 📝 注意事项

1. **Context Clone**:
   - 克隆的 Context 现在完全独立，不会受父 Context 取消影响
   - Trace 信息会自动保留
   - 适用于异步操作和后台任务

2. **CPU 指标采集**:
   - 需要 gopsutil 库（已在依赖中）
   - 某些环境下可能采集失败（如容器环境），会自动降级
   - 失败时不会影响限流器正常工作

3. **HTTPClient**:
   - 建议优先使用 `DoJSON()`, `DoString()`, `DoBytes()` 等自动关闭方法
   - 如果使用 `Do()`，必须手动 `defer resp.Close()`
