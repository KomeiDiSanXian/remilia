# V2 渐进迁移测试策略

> 目标：允许大规模重构，同时保持足够的安全性与可回归性。

## 为什么迁移期不建议删除全部测试

“先删光测试、后面再补”短期看起来爽，但多数情况下会让迁移变成不可控的重写：

- Engine 并发细节多：race、shutdown 退化很难靠肉眼重新发现。
- 现有测试隐含了历史踩坑与边界条件。
- 没有测试会导致验收标准模糊：你很难区分行为变化是“设计选择”还是“引入 bug”。

## 策略：双轨测试（Dual-track）

### 轨道 A — 现有测试套件（baseline）

- 保持现有测试持续执行。
- 若确实需要改变行为，必须明确说明并更新断言（附理由）。

### 轨道 B — 面向 V2 的测试套件

为新原语与新契约补充测试，包括：

- `Extensions` 容器正确性与并发安全
- `Context` 语法糖（`Set/Get/All`）是否正确委托给 State extension
- extension 模块（例如 `extension.Command`）的缓存语义

建议：

- 迁移某个能力时，优先为 V2 版本补测试。
- 随后再调整/移除只验证 V1 实现细节的旧测试。

## 临时跳过（Temporary skipping）

迁移早期允许少量测试临时跳过，但需要纪律：

- 使用 `t.Skip("v2 migration")` 并写清 TODO。
- 不允许整包跳过。
- 每个 skip 都要在迁移清单中登记，并在对应阶段回收。

## 工具建议

推荐开发者本地检查：

```bash
# 单元测试
go test ./...

# race（更慢）
go test -race ./...
```

## 验收标准

- 主不变量：每个增量步骤都必须 `go test ./...` 通过。
- 每新增一个 public API surface，至少新增一个对应测试用例。
