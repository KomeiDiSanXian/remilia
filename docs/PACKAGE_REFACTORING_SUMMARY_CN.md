## 🎯 核心问题

### 当前状况

**Root 包过于臃肿**:
- 📁 **130 个 Go 文件** (638 KB 代码)
- 🔀 **200+ 公开 API** 混杂在一起
- 🤯 **认知负担极高**，新手难以上手

**职责混杂**:
```
remilia/
├── 核心引擎 (Engine/Matcher/Context)      ← 应该在 core/
├── 插件系统 (Plugin/PluginManager)        ← 应该在 plugin/
├── 权限系统 (Permission/Role)             ← 应该在 permission/
├── 命令解析 (两套系统并存！)               ← 应该在 command/
├── 规则匹配 (OnCommand/OnKeyword)         ← 应该在 rules/
├── 错误处理 (多种错误混合)                 ← 应该在 errors/
├── 死信队列 (DLQ)                         ← 应该在 deadletter/
└── 基础设施 (已有 infra/ 但 root 仍有重复) ← 清理 compat.go
```

---

## 💡 解决方案

### 目标架构

```
remilia/                      # 用户入口 + 兼容层 (40 文件)
├── bot.go                   # 主入口
├── compat.go                # 类型别名（向后兼容）
└── doc.go                   # 包文档

├── core/                    # [P2-长期] 核心引擎
│   ├── engine.go
│   ├── matcher.go
│   └── context.go

├── plugin/                  # [P0-立即] 插件系统
│   ├── plugin.go
│   ├── manager.go
│   └── base.go

├── permission/              # [P0-立即] 权限系统
│   ├── permission.go
│   ├── role.go
│   └── middleware.go

├── command/                 # [P1-中期] 命令解析（合并双轨）
│   ├── parser.go
│   └── enhanced.go

├── rules/                   # [P1-中期] 匹配规则
│   └── rules.go

├── errors/                  # [P1-中期] 错误处理
│   └── errors.go

├── deadletter/              # [P1-中期] 死信队列
│   └── queue.go

├── middleware/              # [已有] 标准中间件
├── infra/                   # [已有] 基础设施
├── config/                  # [已有] 配置管理
└── openapi/                 # [已有] API 封装
```

### 迁移策略

**渐进式拆分 + 类型别名兼容**:

```go
// 步骤 1: 创建新包
// remilia/permission/permission.go
package permission

type Permission struct { ... }

// 步骤 2: Root 包添加别名（保持兼容）
// remilia/compat.go
package remilia

import "github.com/KomeiDiSanXian/remilia/permission"

// Deprecated: 使用 permission.Permission
type Permission = permission.Permission
```

**时间表**:
```
v0.8.0 (2026 Q1) → 创建新包 + 添加别名
v0.9.0 (2026 Q2) → 标记旧 API 为 Deprecated
v0.10.0 (2026 Q3) → 移除别名（编译错误提示迁移）
v1.0.0 (2026 Q4) → 完整重构（可选）
```

## 🔍 关键决策点

### 决策 1: 是否拆分 core 包？

**推荐**: ❌ **暂不拆分**

**理由**:
- 影响所有用户代码（破坏性变更）
- 需要重新设计公开 API
- 可在 v1.0.0 时重新评估

**替代方案**:
- 通过 `internal/core` 试验新设计
- 收集社区反馈后决策

### 决策 2: 命令系统保留哪套？

**推荐**: ✅ **统一到增强系统**

**理由**:
- 功能更强大（类型检查、参数验证）
- 社区呼声高
- 符合现代 CLI 框架趋势

**迁移路径**:
```go
// 旧方式（废弃）
args, _ := ctx.ParseCommand()

// 新方式（推荐）
import "github.com/KomeiDiSanXian/remilia/command"
cmd, _ := command.Parse(ctx)
```

### 决策 3: 兼容期多长？

**推荐**: ✅ **2-3 个版本（6-9 个月）**

**理由**:
- 给用户足够迁移时间
- 符合 Go 社区实践（如 `io/ioutil` 废弃）
- 平衡维护成本与用户体验

**时间表**:
- v0.8.0: 新旧并存
- v0.9.0: 标记废弃
- v0.10.0: 移除旧 API
