### 1. AdaptiveRateLimiter 中的信号量大小调整竞态条件

**文件**: `middleware/adaptive.go`  
**问题描述**:

```go
func (arl *AdaptiveRateLimiter) adjustLimit(newLimit int32) {
    arl.mu.Lock()
    defer arl.mu.Unlock()
    
    old := arl.maxConcurrency.Swap(newLimit)
    
    // 问题：在调整 sema channel 大小时，可能有请求正在等待
    newSema := make(chan struct{}, newLimit)
    
    // 迁移现有令牌
    oldSema := arl.sema
    close(oldSema) // 这会导致所有等待的 goroutine 收到 zero value
    
    arl.sema = newSema
}
```

**风险**:
- 关闭旧的 `sema` channel 会导致正在等待的 goroutine 收到零值，可能导致逻辑错误
- 令牌迁移过程中可能丢失正在使用的令牌计数
- 并发请求可能在切换期间获得不正确的许可

**影响**: 可能导致限流失效或请求被错误拒绝

**修复建议**:
```go
func (arl *AdaptiveRateLimiter) adjustLimit(newLimit int32) {
    arl.mu.Lock()
    defer arl.mu.Unlock()
    
    old := arl.maxConcurrency.Load()
    if old == newLimit {
        return
    }
    
    arl.maxConcurrency.Store(newLimit)
    
    // 方案1：不替换 channel，而是使用计数器控制
    // 方案2：使用加权信号量（golang.org/x/sync/semaphore）
    // 避免直接关闭和替换 channel
}
```

**收益**: 消除限流器中的竞态条件，提升系统稳定性

### 2. WebhookServerAdapter 中的 Goroutine 泄漏风险

**文件**: `webhook_adapter.go`  
**问题描述**:

```go
func (a *WebhookServerAdapter) Start(ctx context.Context, handler func(*dto.Payload)) error {
    // 启动多个 worker goroutines
    for i := 0; i < a.workers; i++ {
        a.wg.Add(1)
        go func() {
            defer a.wg.Done()
            for {
                select {
                case <-a.ctx.Done():
                    return
                case event, ok := <-eventStream:
                    if !ok {
                        return
                    }
                    // 如果 handler 阻塞，goroutine 也会阻塞
                    safeHandleEvent(handler, event)
                }
            }
        }()
    }
    
    // 问题：如果 HTTP 服务器启动失败，workers 可能永远运行
}
```

**风险**:
- 如果 HTTP 服务器启动失败，worker goroutines 仍在运行
- `eventStream` channel 如果未正确关闭，workers 将永远阻塞
- Stop 超时时，可能有 goroutines 泄漏

**影响**: 资源泄漏，长期运行后可能耗尽内存

**修复建议**:
```go
func (a *WebhookServerAdapter) Start(ctx context.Context, handler func(*dto.Payload)) error {
    // ... 现有代码 ...
    
    // 启动 HTTP 服务器前检查 webhook 状态
    if a.webhook == nil {
        a.cancel() // 取消所有 workers
        a.wg.Wait() // 等待清理
        return errutil.ErrWebhookCreateFailed
    }
    
    // 在 HTTP 服务器启动失败时清理
    a.wg.Go(func() {
        if err := a.server.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            logger.WithError(err).Error("[WebhookServerAdapter] Server failed")
            a.cancel() // 确保 workers 停止
        }
    })
}
```

**收益**: 防止 goroutine 泄漏，减少资源消耗

### 3. CircuitBreaker 半开状态的竞态条件

**文件**: `middleware/circuitbreaker.go`  
**问题描述**:

```go
func (cb *CircuitBreaker) canExecute() error {
    state := cb.GetState()
    
    switch state {
    case StateHalfOpen:
        // 检查半开状态超时
        halfOpenStart := cb.halfOpenStarted.Load().(time.Time)
        if !halfOpenStart.IsZero() && cb.config.HalfOpenTimeout > 0 {
            if time.Since(halfOpenStart) >= cb.config.HalfOpenTimeout {
                // 问题：多个 goroutine 可能同时检测到超时
                cb.state.Store(StateOpen)
                cb.lastFailure.Store(time.Now())
                // 缺少同步保护
            }
        }
        
        // 半开状态下限制请求数量
        for {
            current := cb.halfOpenReqs.Load()
            if current >= int32(cb.config.HalfOpenMaxRequests) {
                return fmt.Errorf("...")
            }
            // 问题：CAS 循环可能无限重试
            if cb.halfOpenReqs.CompareAndSwap(current, current+1) {
                break
            }
        }
    }
}
```

**风险**:
- 多个请求可能同时将状态从 HalfOpen 转为 Open
- CAS 循环在高并发下可能导致 CPU 空转
- 状态转换缺少原子性保护

**影响**: 熔断器行为不确定，可能导致过度保护或保护失效

**修复建议**:
```go
func (cb *CircuitBreaker) canExecute() error {
    for attempts := 0; attempts < 100; attempts++ { // 限制重试次数
        state := cb.GetState()
        
        switch state {
        case StateHalfOpen:
            halfOpenStart := cb.halfOpenStarted.Load().(time.Time)
            
            // 使用互斥锁保护状态转换
            if !halfOpenStart.IsZero() && cb.config.HalfOpenTimeout > 0 {
                if time.Since(halfOpenStart) >= cb.config.HalfOpenTimeout {
                    cb.mu.Lock()
                    // Double-check
                    if cb.GetState() == StateHalfOpen {
                        cb.setState(StateOpen)
                        cb.lastFailure.Store(time.Now())
                    }
                    cb.mu.Unlock()
                    return fmt.Errorf("circuit breaker is open")
                }
            }
            
            // 限制 CAS 重试次数
            current := cb.halfOpenReqs.Load()
            if current >= int32(cb.config.HalfOpenMaxRequests) {
                return fmt.Errorf("...")
            }
            if cb.halfOpenReqs.CompareAndSwap(current, current+1) {
                return nil
            }
        }
    }
    return fmt.Errorf("too many concurrent state transitions")
}
```

**收益**: 提升熔断器可靠性，避免状态混乱

### 7. Retry 中间件的 Context 取消检查不足

**文件**: `middleware/retry.go`  
**问题描述**:

```go
func Retry(cfg RetryConfig) eventctx.Middleware {
    return func(next eventctx.Handler) eventctx.Handler {
        return func(ctx *eventctx.Context) error {
            for attempt := 0; attempt <= cfg.MaxAttempts; attempt++ {
                err := next(ctx)
                
                if err == nil {
                    return nil
                }
                
                // 问题：没有在每次重试前检查 context 是否已取消
                // 可能继续重试已取消的操作
                
                delay := min(cfg.BackoffBase*time.Duration(1<<uint(attempt)), cfg.BackoffMax)
                
                if !sleepWithContext(ctx.Context(), delay) {
                    return engine.NewBlockError("retry canceled")
                }
            }
        }
    }
}
```

**风险**:
- Context 取消后仍可能执行多次重试
- 浪费资源处理已取消的请求
- 影响优雅关闭的速度

**影响**: 资源浪费，关闭延迟

**修复建议**:
```go
func Retry(cfg RetryConfig) eventctx.Middleware {
    return func(next eventctx.Handler) eventctx.Handler {
        return func(ctx *eventctx.Context) error {
            for attempt := 0; attempt <= cfg.MaxAttempts; attempt++ {
                // 在每次重试前检查 context
                select {
                case <-ctx.Context().Done():
                    return engine.NewBlockError("retry canceled before attempt")
                default:
                }
                
                err := next(ctx)
                
                if err == nil {
                    return nil
                }
                
                // ... 现有重试逻辑
            }
        }
    }
}
```

**收益**: 提升资源利用率，加速优雅关闭

### 8. Lifecycle Manager 的 Stop 超时处理

**文件**: `lifecycle/lifecycle.go`  
**问题描述**:

```go
func (m *Manager) Stop(ctx context.Context) error {
```

- 多个组件停止失败时，只能看到最后一个错误
- 无法知道哪些组件停止失败
- 超时后可能有组件未正确清理

**影响**: 资源泄漏，错误信息丢失

**修复建议**:
```go
func (m *Manager) Stop(ctx context.Context) error {
    var errs []error
    
    for i := len(m.components) - 1; i >= 0; i-- {
        comp := m.components[i]
        
        if err := comp.OnStop(ctx); err != nil {
            errs = append(errs, fmt.Errorf("component %s: %w", comp.Name(), err))
            // 继续停止其他组件
        }
    }
    
    if len(errs) > 0 {
        return fmt.Errorf("stop errors: %v", errs)
    }
    return nil
}
```

**收益**: 改善错误追踪，提升可调试性

```go
    if err != nil || len(percent) == 0 {

    runtime.ReadMemStats(&m)

    arl.memoryUsage.Store(memUsage)

```

### 11. Plugin Manager 依赖解析可能死循环

**文件**: `plugin/manager.go`  
**问题描述**:

虽然当前代码有循环依赖检测，但在某些复杂场景下（如间接循环依赖）可能检测不到：

```
A -> B -> C -> A  （能检测）
A -> B -> D
B -> C -> E
D -> E -> A       （可能漏检）
```

**风险**:
- 复杂依赖图可能形成循环
- 依赖解析陷入死循环或栈溢出
- 插件加载失败

**影响**: 插件系统启动失败

**修复建议**:
```go
// 使用拓扑排序算法（Kahn's Algorithm）
func (m *Manager) resolveDependencies(plugins []*PluginInstance) ([]*PluginInstance, error) {
    // 1. 构建依赖图
    inDegree := make(map[string]int)
    graph := make(map[string][]string)
    
    for _, p := range plugins {
        inDegree[p.Name()] = len(p.desc.Deps)
        for _, dep := range p.desc.Deps {
            graph[dep] = append(graph[dep], p.Name())
        }
    }
    
    // 2. 拓扑排序
    queue := []string{}
    for name, degree := range inDegree {
        if degree == 0 {
            queue = append(queue, name)
        }
    }
    
    result := []*PluginInstance{}
    for len(queue) > 0 {
        current := queue[0]
        queue = queue[1:]
        
        // 找到插件实例
        for _, p := range plugins {
            if p.Name() == current {
                result = append(result, p)
                break
            }
        }
        
        // 减少依赖计数
        for _, next := range graph[current] {
            inDegree[next]--
            if inDegree[next] == 0 {
                queue = append(queue, next)
            }
        }
    }
    
    // 3. 检查循环依赖
    if len(result) != len(plugins) {
        return nil, fmt.Errorf("circular dependency detected")
    }
    
    return result, nil
}
```

**收益**: 彻底解决循环依赖问题

### 12. 统一错误处理和包装

**当前状态**: 错误处理分散在多个包中，缺少统一的错误分类和包装策略。

**改进建议**:
```go
// 定义标准错误类型
type ErrorCode string

const (
    ErrCodeValidation    ErrorCode = "VALIDATION_ERROR"
    ErrCodeRateLimit     ErrorCode = "RATE_LIMIT_EXCEEDED"
    ErrCodeCircuitOpen   ErrorCode = "CIRCUIT_OPEN"
    ErrCodeTimeout       ErrorCode = "TIMEOUT"
    ErrCodeInternal      ErrorCode = "INTERNAL_ERROR"
)

type FrameworkError struct {
    Code    ErrorCode
    Message string
    Cause   error
    Details map[string]interface{}
}

func (e *FrameworkError) Error() string {
    if e.Cause != nil {
        return fmt.Sprintf("[%s] %s: %v", e.Code, e.Message, e.Cause)
    }
    return fmt.Sprintf("[%s] %s", e.Code, e.Message)
}
```

```go
func (e *Engine) ProcessEventsBatch(events []*dto.Payload, batchSize int) []error {
    errors := make([]error, len(events))
    
    for i := 0; i < len(events); i += batchSize {
        end := min(i+batchSize, len(events))
        batch := events[i:end]
        
        var wg sync.WaitGroup
        for j, event := range batch {
            wg.Add(1)
            go func(idx int, evt *dto.Payload) {
                defer wg.Done()
                ctx := context.NewContext(evt, nil)
                if err := e.ProcessEvent(ctx); err != nil {
                    errors[i+idx] = err
                }
            }(j, event)
        }
        wg.Wait()
    }
    
    return errors
}
```
