## 📊 核心结论（TL;DR）

### 当前问题

```
remilia/ (root package)
├─ 130 个 Go 文件 (638 KB)
├─ 200+ 公开 API 混杂
├─ 职责边界不清（引擎/插件/权限/命令/规则...）
└─ 维护成本高，新手难上手
```

### 解决方案

**渐进式拆分 + 兼容性保证**

```
Phase 1 (P0) - 1-2 个月:
├─ permission/    (权限系统)
├─ plugin/        (插件系统)
└─ 清理 infra/*   (基础设施)
→ Root 包减少到 40 文件

Phase 2 (P1) - 3-6 个月:
├─ command/       (统一命令系统)
├─ rules/         (匹配规则)
├─ errors/        (错误处理)
└─ deadletter/    (死信队列)
→ Root 包减少到 30 文件

Phase 3 (P2) - 6-12 个月 (可选):
└─ core/          (核心引擎)
→ v1.0.0 架构升级
```

### 关键指标

| 指标 | 现状 | Phase 1 | Phase 2 | 改善 |
|------|------|---------|---------|------|
| Root 包文件数 | 130 | 40 | 30 | **77%↓** |
| 公开 API 数量 | 200+ | 80 | 60 | **70%↓** |
| 认知负担 | 高 | 中 | 低 | **显著改善** |
| 投入成本 | - | 18 人日 | 52 人日 | - |
| 第一年 ROI | - | - | **+35%** | 第二年 **+169%** |

| 阶段 | 优先级 | 工作量 | 风险 | 收益 | 建议 |

## 🔑 关键决策点

### 决策 1: 是否启动重构？

**推荐**: ✅ **是**，优先执行 Phase 1 (P0)

**理由**:
- 快速见效（1-2 个月）
- 低风险（无破坏性变更）
- 高收益（降低 15% 复杂度）
- 用户无感知（类型别名兼容）

### 决策 2: 是否拆分 core 包？

**推荐**: ❌ **暂不拆分**，在 Phase 1-2 完成后重新评估

**理由**:
- 影响极大（所有用户代码）
- 需要破坏性变更（v1.0.0）
- 先通过 P0/P1 收集数据和反馈

### 决策 3: 命令系统保留哪套？

**推荐**: ✅ **统一到增强系统** (`command/` 包)

**理由**:
- 功能更强大（类型检查、参数验证）
- 符合现代 CLI 框架趋势
- 社区呼声高

### 决策 4: 兼容期多长？

**推荐**: ✅ **2-3 个版本**（6-9 个月）

**时间表**:
- v0.8.0: 新旧并存，无警告
- v0.9.0: 旧 API 标记 Deprecated
- v0.10.0: 移除旧 API，编译错误
