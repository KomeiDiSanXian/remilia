# Remilia 吞吐量测试

这个基准测试程序用于测试 Remilia Bot 框架在不同负载下的性能表现。

## 测试版本

### 1. 单场景快速测试（推荐）

**文件**: `single_scenario.go`

- ✅ 快速运行（约 15 秒）
- ✅ 稳定可靠，无 WaitGroup 问题
- ✅ 测试中等负载 (1000 msg/s)
- ✅ 详细的性能报告

```bash
cd examples/benchmark
go run single_scenario.go
```

### 2. 多场景完整测试

**文件**: `throughput_bench.go`

- 📊 测试 4 个负载场景
- ⏱️ 总时长约 2-3 分钟
- 📈 全面的性能分析
- ⚠️ 场景间需要冷却时间

```bash
cd examples/benchmark
go run throughput_bench.go
```

## 测试场景

程序包含 4 个预设的测试场景：

1. **低负载** (100 msg/s) - 10 并发客户端，每个 10 msg/s
2. **中等负载** (1000 msg/s) - 50 并发客户端，每个 20 msg/s
3. **高负载** (5000 msg/s) - 100 并发客户端，每个 50 msg/s
4. **极限负载** (10000 msg/s) - 200 并发客户端，每个 50 msg/s

## 测试指标

测试会输出以下性能指标：

### 📊 基础指标
- **总消息数**: 发送的消息总数
- **成功处理**: 成功处理的消息数量和百分比
- **处理失败**: 失败的消息数量和百分比
- **处理中/丢失**: 未完成处理的消息数量

### 🚀 吞吐量
- **实际吞吐量**: 每秒处理的消息数 (msg/s)
- **目标达成率**: 实际吞吐量与目标吞吐量的比率

### ⏰ 延迟统计
- **平均延迟**: 消息处理的平均延迟
- **最小延迟**: 最快的处理时间
- **最大延迟**: 最慢的处理时间

### 🔌 API 调用
- **总调用次数**: Mock API 被调用的总次数

## 自定义测试

你可以修改 `main()` 函数中的测试场景来自定义测试参数：

```go
scenarios := []struct {
    name   string
    config BenchmarkConfig
}{
    {
        name: "自定义测试",
        config: BenchmarkConfig{
            Duration:          30 * time.Second,  // 测试时长
            ConcurrentClients: 100,               // 并发数
            MessageRate:       100,               // 每客户端速率
            EnableMiddleware:  true,              // 启用中间件
            EventType:         dto.C2CMessageCreate,
        },
    },
}
```

## 注意事项

1. **Mock 组件**: 测试使用 Mock Adapter 和 Mock OpenAPI，不会发起真实的网络请求
2. **内存使用**: 高并发场景可能消耗较多内存，建议监控系统资源
3. **CPU 密集**: 测试会充分利用 CPU，建议在空闲环境运行
4. **结果波动**: 实际性能受系统负载、CPU 性能等因素影响

## 性能优化建议

基于测试结果，你可以：

1. **调整并发限制**: 使用 `middleware.ConcurrencyLimit`
2. **优化处理器**: 减少 Handler 中的阻塞操作
3. **启用池化**: 使用对象池减少内存分配
4. **调整缓冲区**: 增大 Channel buffer 大小

## 与真实环境对比

测试环境与生产环境的主要区别：

| 项目 | 测试环境 | 生产环境 |
|------|---------|---------|
| 网络延迟 | ~1ms (Mock) | 50-200ms (真实 API) |
| 消息来源 | 程序生成 | Webhook 接收 |
| 并发模式 | 可控并发 | 随机突发 |
| 错误处理 | 简化逻辑 | 完整处理 |

因此，**生产环境的实际吞吐量通常为测试值的 20-40%**。

## 故障排查

### 消息丢失严重
- 增大 Mock Adapter 的 buffer 大小
- 降低消息生成速率
- 检查系统资源是否充足

### 延迟过高
- 减少中间件数量
- 优化 Handler 逻辑
- 检查是否有阻塞操作

### 内存持续增长
- 检查是否有 goroutine 泄漏
- 验证资源正确释放
- 使用 pprof 分析内存使用
